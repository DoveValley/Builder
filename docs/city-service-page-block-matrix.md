# City Service Page block matrix (Phases 1, 2 & 3: picker + bridge + live preview + FAQ accordion)

Lets an agency choose which real-research-backed topics appear on a client's city pages, via a
"City Service Page" tab in `admin/client.php`, next to the Service Area Page tab. Phase 1 covers the
picker UI and the content-generation bridge; Phase 2 adds a live preview pane; Phase 3 adds an FAQ
accordion display option. Phase 3 was deliberately scoped down from four planned variant types to this
one — see `project_city_service_page_block_matrix_scope` in memory for the SEO-grounded reasoning behind
dropping the other three.

## The three-tier section model

Every city page (`includes/landing_page_clients.php`, `lpc_default_page_data()`) is built from three
kinds of sections, and only one of them is what this feature's picker controls:

1. **Spine (4, always-on, not configurable):** Hero, Overview (`city_intro`), FAQ, Service-area+links
   (`related_links`). Generated by the single AI call in `lpc_ai_user_prompt()`/`lpc_generate_page_content()`
   — unchanged by this feature.
2. **Platform furniture (7, always-on, not configurable, not part of this feature at all):** `trust_bar`,
   `safety_toolkit`, `area_map`, `data_chart`, `service_area` (LPC's own auto-computed office/nearby-cities
   widget — **not the same thing** as the spine's "service area + links," which renders as `related_links`
   instead; two different concepts with confusingly similar names), `cta`, `services_list`. All
   auto-computed or fixed by code, never AI-authored, never pickable.
3. **Picked topics (the actual feature) — up to 6 "city pool" + up to 4 "service pool" topics**, chosen
   per client on the City Service Page tab, generated by the bridge described below, and appended after
   the sections above in the page's `sections` array.

There are also two tier-3 sections with no matrix equivalent at all — `feature_columns_local` and
`local_relevance` — generic synthesis slots, still generated by the old single AI call, unaffected by
picks.

**Historical note:** before 2026-11-22, `comparison` (repair_vs_replace), `how_it_works` (process),
`seasonal_calendar` (seasonal_guide), and `why_choose_us` (why_choose_us) were fixed, always-on sections
generated by the old single AI call. They were removed from that call and from `lpc_default_page_data()`'s
fixed schema, because they map directly onto picks — they're now present only if a client actually picks
that topic, generated by the bridge instead.

## Where picks are stored

`client.json`'s `delivery` section (`includes/landing_page_clients.php`, `lpc_default_client_data()`):

```php
'city_block_picks'          => [],   // up to 6 slugs from lpc_city_block_pool()
'service_block_picks'       => [],   // up to 4 slugs from PLUSCITIES_SERVICE_POOL
'vary_blocks_across_cities' => true, // default ON
```

Empty arrays mean "use the platform default" (`lpc_default_block_picks_for_pool()`), same convention
`hub_intro: ''` already uses for the Service Area Page. Because `lpc_load_client()` runs every load
through `lpc_deep_merge_defaults()`, every existing `client.json` on disk picks up these fields
automatically — no migration script needed.

## The city pool is universal, not per-niche — read this before "fixing" it

`lpc_city_block_pool()` returns one fixed list of 9 slugs (`climate_data`, `housing_stock`,
`neighborhoods`, `permits`, `utilities`, `hoa_rules`, `seasonal_guide`, `hazards`, `reviews_from_city`),
used for every client regardless of niche. This looks like it should be resolved per-niche via
PlusCities' own `pluscities_niche_resolved()` (which reads `niche_blueprints/*.json` +
`niche_families/*.json`) — **don't change it back to that without checking current coverage first.**
As of 2026-11-22, PlusCities has blueprints for only 2 niches (`hvac`, `water-damage-restoration`) against
LPC's 7 real active niches (`appliance-repair`, `mold-remediation`, `pest-control`, `plumbing`, `roofing`,
`water-restoration`, `wildlife-control`) — and not one of LPC's real niche slugs matches a PlusCities
blueprint exactly (confirmed live: Meade Restoration's real niche is `water-restoration`, not
`water-damage-restoration`). Per-niche resolution would leave every real client with an empty city pool.
If PlusCities' niche catalog is ever built out to actually cover LPC's real niches, resolving a
per-niche pool becomes viable again — until then, the universal list (which is already generic
local-business content, not restoration-specific) is the correct choice, not a stopgap.

The service pool (`PLUSCITIES_SERVICE_POOL`, `includes/pluscities_lifecycle.php`) was already a fixed
global constant before this feature existed — no change needed there.

## "Vary topics across cities"

`lpc_resolve_block_picks_for_city($client, $city_id, $cityPool, $servicePool)`
(`includes/landing_page_clients.php`): when `vary_blocks_across_cities` is true, each city drops exactly
one of its approved city-pool picks and one approved service-pool pick, chosen by
`crc32($city_id . ':city') % count($picks)` — deterministic (same city always drops the same item),
reproducible, and requires no per-city state. This is deliberately NOT PlusCities' own
`≤50% overlap / word-count balance` selection-rule engine (that's explicitly out of scope — see the memory
doc) — it's a much cheaper mechanism that gets most of the real anti-duplicate-content value.

## The bridge — how picks actually become content

`includes/pluscities_lpc_bridge.php`, called from `lpc_generate_page_content()`
(`includes/landing_page_clients_ai.php`) right after the fixed-sections reset.

**Important architectural choice — this does NOT call `pluscities_create_page()` or
`pluscities_regenerate_block()`.** Those functions hard-require a separate client record
(`pluscities_clients/{id}.json`) that is NOT the same as LPC's real `client.json` and can — confirmed, has
— drift from it (Meade's PlusCities-side record lists only 1 of 2 real cities and 2 of 3 real services).
Building a sync layer between two client records would be exactly the duplicated-state problem this
codebase's own conventions exist to avoid. Instead, this bridge:

- Calls `pluscities_niche_resolved($niche_id)` directly (needs only a niche-id string, no client file) —
  used only for `niche_data_table` content, which gracefully no-ops if no blueprint matches (the common
  case today, see above).
- Builds `$context`/`$clientFacts` straight from LPC's own in-memory `$client` array — never reads
  `pluscities_clients/*.json` at all.
- Calls PlusCities' real, proven writer functions (`pluscities_write_editable_block()`,
  `pluscities_write_automatic_block()`, `pluscities_write_niche_data_table_block()`,
  `includes/pluscities_writer.php`) and fact-card research (`pluscities_fact_card_get_active()`,
  `includes/pluscities_research.php`, which is scoped by city+topic only, never by client) unmodified.
- Still writes into PlusCities' real `blocks` SQL table (`admin/infra/lib/pluscities_db.php`) — same
  schema, same real persistent per-block identity (a stable `id` + `locked` column, useful groundwork for
  a future per-block-lock feature) — but keyed by **LPC's own existing page_id**
  (`{city_id}__{service_id}`), with no corresponding row in PlusCities' own `pages` table at all.

**Key functions:**
- `lpc_pluscities_block_classification($type)` — reads classification from the shared catalog (below),
  not a second copy.
- `lpc_pluscities_fact_topic($type)` — fixes two known slug-mismatch bugs (`hoa_rules`→`hoa`,
  `seasonal_guide`→`seasons`) already flagged in the block catalog's own notes. Fixed here, not in
  PlusCities' own `pluscities_regenerate_block()`, since this bridge doesn't call that function.
- `lpc_ensure_picked_blocks()` — inserts `blocks` rows for newly-picked types; idempotent, checks for an
  existing row by `(page_id, block_type)` first.
- `lpc_regenerate_picked_block()` — per-block dispatch (mirrors `pluscities_regenerate_block()`'s logic):
  `niche_data_table` and `reviews_from_city` gracefully no-op when there's no data to draw from (no niche
  blueprint; LPC's client schema has no stored-reviews field at all); `housing_stock` pulls real Census
  ACS data; everything else routes through the generic editable writer.
- `lpc_build_picked_sections_from_pluscities($page_id)` — reads current `blocks` rows, converts each into
  an LPC section array entry. **Every pick renders as LPC's plain `text` type (heading+body) in Phase 1**
  — PlusCities' generic editable writer only ever produces flat heading+body, never an item list or
  two-column structure, so forcing picks into `highlights`/`steps`/`comparison` shapes would mean
  inventing structure that was never actually generated. Real richer presentations (styled table for
  `niche_data_table`, stat cards for `housing_stock`, carousel for `reviews_from_city`, accordion for FAQ)
  are Phase 3 scope.

## Save ≠ Generate

Saving the City Service Page tab (`admin/client_save.php`, `case 'city_service_page_settings'`) only
persists picks — free, instant, no AI cost, does not call the bridge at all. Applying new picks to an
already-existing page requires the Target Cities × Services grid's existing "Generate/Refresh Selected →
Regenerate text content ($)" action — same cost-gated mechanism that already existed, nothing new.

## The admin UI

`admin/client.php`, `$tab === 'city_service_page'`. Reuses the descriptions in
`includes/pluscities_block_catalog.php` (factored out of `admin/platform_info.php`'s internal
documentation page so there's one source, not two that can drift) but translates classification into
plain language via `pluscities_block_class_label()` — "AI-written" / "Pulled from real data" / "Your own
content" — never surfacing internal terms like "editable"/"automatic"/"client-supplied" to agencies.
Count enforcement (max 6 city, max 4 service) is JS-assisted but server-authoritative
(`admin/client_save.php` re-validates against the real pools regardless of what the client sent).

## Phase 2 — live preview

A "Show Preview" button/panel on the City Service Page tab, updating as you check/uncheck topics — no
Save needed, no AI cost, no new rendering logic.

**Key decision: reuses `lpc_preview_render()` (`includes/landing_page_clients_publish.php`) unchanged**
instead of writing a JS mirror (the originally-scoped Phase 2 plan, written before Phase 1 existed, assumed
~9 separate templates for different section shapes — unnecessary once Phase 1 confirmed every picked topic
renders as the plain `text` type, which this function already handles). `lpc_preview_render()` is pure,
WordPress-independent, and already used by `page_editor.php`'s own `?preview=1` mode and
`admin/preview_site.php` — reusing it means zero new rendering code and zero future-drift risk.

- `lpc_build_preview_sections($client_id, $cityPicks, $servicePicks)` (`includes/pluscities_lpc_bridge.php`):
  for each currently-checked topic, looks for real already-generated content across ALL of this client's
  existing pages in one query (not just an arbitrary "first" page — `lpc_list_pages()` sorts alphabetically,
  so checking only the first page_id would arbitrarily miss real content that exists elsewhere, confirmed
  live against Meade Restoration). Falls back to a clearly-labeled placeholder (catalog display name + the
  catalog's own `what` description) when no real content exists yet for that topic — the expected case for
  a brand-new client.
- `lpc_pluscities_flatten_content($blockType, $content)` — the `content_json` → `{heading, body}` shaping
  logic (including the `housing_stock`/`niche_data_table` label formatting) was extracted out of
  `lpc_build_picked_sections_from_pluscities()` into its own function specifically so the preview and the
  real generated page can never show differently-formatted text for the same stored content.
- New AJAX case `city_service_page_preview` (`admin/client_save.php`) — reads the CURRENTLY CHECKED
  checkboxes from POST (ephemeral, never saved), same CSRF/whitelist handling as the real save case, returns
  `{html}` via `lpc_preview_render()`. JS mirrors the Service Area Page tab's own
  `toggleLpcSapPreview()`/`lpcSapUpdatePreview()` pattern exactly.

**A real production bug was fixed as a prerequisite, not deferred:** `lpc_preview_render()`'s `text` case
and the WP-plugin's `lpc_render_text()` (`wp-plugin/landing-page-client/includes/renderer.php`) both wrapped
`body` in a single `<p>` with no line-break handling — `housing_stock`/`niche_data_table`'s multi-line
bodies were collapsing into a run-on paragraph **on the real live Meade Restoration pages already generated
during Phase 1 QA**, not just a hypothetical preview. Fixed in both places with `nl2br()` around the
already-escaped body.

## Phase 3 — FAQ display style (accordion)

A "Display as: List | Accordion" control next to the FAQ row in the City Service Page tab's "Always
included" card. Only FAQ got a real variant — the original Phase 3 plan covered three more (highlights
card/list toggle, niche-table and reviews-from-city renderers), all dropped 2026-11-22 after an
SEO-grounded review (Scott: "what's better for SEO ranking"): the highlights toggle would've been pure
styling once Phase 1 confirmed there's no item list left to arrange (zero SEO value), and the other two
would be built for content that cannot exist for any real client today (no niche blueprints, no reviews
field in LPC) — real rendering work with zero current payoff. See
`project_city_service_page_block_matrix_scope` in memory for the full reasoning.

**Schema needed zero changes — verified, not assumed.** `lpc_assemble_schema()`
(`includes/landing_page_clients_publish.php`) already derives FAQPage JSON-LD mechanically from the `faq`
section's `items` array, completely independent of display style — confirmed directly: toggling
`faq_display_style` and rebuilding the schema produces byte-identical output either way.

**Where the setting lives and how it reaches the renderer:**
- `client.json`'s `delivery.faq_display_style` ('list' default | 'accordion') — same simple-string-field
  convention `hub_city_format` already uses, same `city_service_page_settings` save case, its own small
  form (not gated behind a pick checkbox — FAQ is spine/always-on).
- `lpc_rebuild_manifest()` copies it into the manifest's existing `settings` block, same home
  `hub_intro`/`hub_city_format` already live in.
- **Real plumbing gap found and fixed:** `lpc_render_single_page()` didn't receive the manifest at all
  before this — `$manifest` was in scope at its call site (`lpc_handle_route()`,
  `wp-plugin/landing-page-client/includes/rewrite.php`) but never passed through. Now threaded:
  `lpc_handle_route()` → `lpc_render_single_page($page, $top_level, $manifest)` →
  `lpc_render_sections($sections, $hero_level, $faq_style)` → `lpc_render_faq($section, $faq_style)`.

**The accordion itself — native `<details>/<summary>`, no custom JS.** `lpc_render_faq()`
(`renderer.php`) emits `<details class="lpc-faq-item"><summary>{q}</summary><p>{a}</p></details>` per
item when the style is `accordion`, same `.lpc-faq-list`/`.lpc-faq-item` wrapper classes as the `list`
variant so the existing CSS applies to both — only `summary` needed its own small addition in
`styles.php` (remove the default disclosure marker, add a rotating +/− indicator in the client's own
accent color). Chosen over a JS-driven collapse because content stays in the DOM regardless of
open/closed state (no crawlability risk) and it works with zero JavaScript.

**`lpc_preview_render()`'s `faq` case is intentionally unchanged** — it stays plain `<h3>`/`<p>` regardless
of the live setting, consistent with its own doc comment that it's bare structural content-proofing, not
a visual approximation of the live theme.

**Verified:** the `list` default produces byte-identical output to pre-Phase-3 behavior (confirmed via
direct comparison); FAQPage schema confirmed unaffected by the setting either way; no AI/API cost involved
anywhere in this phase.

## Known gaps / what still needs real content, not code

- `reviews_from_city` always gracefully no-ops today — LPC's client schema has no stored-reviews field at
  all (unlike PlusCities' own client record, which has `reviews_by_city`). Picking it is harmless but
  produces nothing until a real reviews data entry point exists somewhere in LPC.
- `niche_data_table` always gracefully no-ops for any of LPC's 7 real niches today (see "city pool is
  universal" above — same root cause, no matching PlusCities niche blueprint).
- Per-block locking does not exist yet. Page-level lock (`$page['locked']`) is respected everywhere this
  bridge touches (checked before any regeneration happens at all), but there's no way to protect one
  hand-edited picked section while regenerating the rest of the page.
